OTE

Embeddable OTE widgets

opentechevents.org
Component v__EMBED_VERSION__ OTE Spec v__OTE_SPEC_VERSION__

Two Web Components that render or link to events from any OTE JSON feed. No framework, no build step, no package to install — one <script> tag and one element.

  • Events widget (<ote-events>) — renders upcoming events as calendar, list, or cards. Key attributes: feed/feeds, layout, views, theme, fields-preview/fields-detail, event-actions, group-events; JS API: el.events, el.eventActions(context).
  • Subscribe widget (<ote-subscribe>) — a "subscribe to this feed" trigger for Calendar (Google Calendar, webcal://, ICS), RSS (Feedly, feed://), and OTE feed links. Key attributes: feed-ics, feed-rss, feed-json, show, convert, layout.
  • Reference — versioned script URLs, SemVer policy, the host-app integration API, and the agent-facing guide.

Checking the feed…

Both widgets read this one URL, and it is the only file you have to publish: the OTE converter derives the calendar (ICS) and RSS feeds from it.

Several URLs, comma-separated, combine into one events widget. The page keeps the value in its address, so you can share a playground already pointed at your own feed.

Optional height budget for the widget: px, rem, em, ch, vh, dvh, svh, vmin or vmax (a bare number is read as pixels). Anything else, including calc() and %, leaves the widget unbounded. What does not fit scrolls inside the widget, so you no longer need to wrap it in your own max-height/overflow container — a wrapper scrolls the widget from the outside, which carries the calendar's weekday header and the list's column header away with it. It is a maximum, not a fixed height: a short feed still renders at its natural height. In layout="calendar" the weeks share the budget instead of each reserving max-per-day events' worth of height, so empty weeks stop taking room they do not use. Rows never shrink below a day showing one event beside a +N more link; past that the grid scrolls with the weekday header pinned. So max-per-day is "as many as fit" while a budget is set. For a sparse feed try max-per-day="off" with it: that mode sizes each week to its own content, so empty weeks collapse instead of reserving room — often enough to drop the scrollbar entirely.

A strip under the events carrying the feed's name (linked to the publisher's own page when the document declares url), the time zone the times are rendered in, an <ote-subscribe> and the OTE mark. On by default, so upgrading a floating /embed/latest/ embed changes what the page renders; a pinned /embed/v<x.y.z>/ URL is untouched. auto renders it only when the widget knows where the data came from — for a host app driving the widget through .events = […] that is nothing, so it renders nothing. It is chrome inside the max-height budget: the events scroll under it.

The footer's subscribe element gets the feed URL the widget already fetched, plus the text/calendar and application/rss+xml entries of the document's own alternates (OTE Spec 0.5+) — so your own ICS is offered instead of a generated one. feed-ics, feed-rss and convert on <ote-events> are passed straight through to it and outrank the document; convert="off" is how you stop convert.opentechevents.org URLs from being built for your visitors at all. With feeds="a,b" there is no single document, so the strip names the source count and offers no subscribe.

The shape of the <ote-subscribe> the footer mounts. badges names the formats on the strip itself; menu is one Subscribe trigger, which is quieter when the converter supplies three groups. Note the default differs from the standalone element's, which is menu.

The "Powered by OTE" link to the spec — the "this is an open feed, you can take it with you" affordance. Off for a site whose own footer already says it; the subscribe links stay either way, which turning the whole footer off would lose.

Cards layout only. Minimum card width in the responsive grid — also accepts any raw CSS length via the attribute (e.g. card-width="280px"), or set --ote-card-min-width directly in CSS.

Calendar layout only. How many events a day cell shows before the rest collapse into a +N more popover. max-per-day="off" stacks every event, which is what a busy day did before this attribute existed.

How much room a day cell gives each event. auto uses the compact metrics when max-height is set and the comfortable ones otherwise — a budget means height is scarce, and comfortably a single event costs about 5.8em of cell against 3.4em compact. Set it explicitly to override either way.

Which month the calendar opens on. next-event opens on the next upcoming event — or the most recent past one for a feed that is entirely in the past — so a feed starting next March does not open on an empty current month. The attribute also takes a fixed YYYY-MM or YYYY-MM-DD.

On by default. Below 600px of container width (not viewport — the widget is usually in a column) the month grid becomes a list, because seven columns at phone width truncate both the weekday headers and every event title. Unchecking it is responsive="off".

views

The views a visitor may switch between, in the header above the events — which also carries Today, the month arrows and the month itself in layout="calendar", in that order. layout is then only the view the widget opens on. The control shows labels while they fit, icons when they do not, and a native dropdown in a narrow column; the widget measures itself to decide. All three by default, so upgrading a floating /embed/latest/ embed changes what the page renders; a pinned /embed/v<x.y.z>/ URL is untouched. Clear every box (views="none") to keep the layout the embedder chose, and note that a one-view list renders no row either. A host app driving the widget through .events = […] gets no switcher unless it asks for one with this attribute: it owns its own view chrome. Like the footer it is chrome inside the max-height budget — the events scroll under it — and the choice lives in memory only: the widget writes nothing to storage or to your page's URL, and reports each change as an ote-view-change event if you want to remember it yourself.

group-events

Cards layout only. Collapses events that share the same partOf.id into one stacked card with a badge; the detail modal gains prev/next between occurrences. Off by default. To try it, switch to JSON source mode above and paste events whose partOf field shares an id, e.g. "partOf": {"id": "https://example.org/series/monthly", "type": "series"}.

Versioning

Production embeds should use a fixed version URL so future widget changes do not alter existing sites without an explicit upgrade.

Recommended
https://tools.opentechevents.org/embed/v__EMBED_VERSION__/ote-events.js
Automatic updates
https://tools.opentechevents.org/embed/latest/ote-events.js
Legacy alias
https://tools.opentechevents.org/embed/ote-events.js

The widget follows semantic versioning: patch releases are compatible fixes, minor releases add compatible features, and major releases may require migration. Check the changelog before changing the version used by a production page.

Component versions and OTE Spec versions are independent. The component version tells you which widget bundle you are loading; the OTE Spec version tells you which event/feed shape that bundle is designed to consume.

OTE Spec 0.4.0 lets a feed publish an http:// image. On an https page the browser blocks such an address as mixed content, so the widget treats that image as absent — cards show their placeholder (or your placeholder-image) and the detail view renders without one, instead of showing a frame that can never load. If an event lists several images, the first https:// one is used even when an http:// entry comes before it.

Host app integration

Apps such as OTE Reader can pass already-filtered events in memory and keep subscriptions, folders, read state, and persistence outside the widget. Use sort="none" when the host app owns ordering. 

await customElements.whenDefined("ote-events");

const widget = document.querySelector("ote-events");
widget.setAttribute("sort", "none");
widget.setAttribute("event-actions", "none");
widget.events = filteredEvents.map((event) => ({
  ...event,
  _feedUrl: event.feedUrl,
  _feedTitle: event.feedTitle,
}));

widget.eventActions = (context) => [{
  id: "save",
  label: saved.has(context.originalEvent.id) ? "Saved" : "Save",
  icon: saved.has(context.originalEvent.id) ? "bookmark" : "star",
  pressed: saved.has(context.originalEvent.id),
  placement: "preview",
  onClick(_previewEvent, actionContext) {
    saveEvent(actionContext.originalEvent.id, actionContext.feed?.url);
  },
}];

widget.eventClassName = (context) =>
  read.has(context.originalEvent.id) ? "is-read" : "is-unread";
widget.eventBadges = (context) =>
  context.originalEvent.cfpOpen ? [{ label: "CFP", icon: "plus" }] : [];
API Use
el.events Render an in-memory array of OTE events without fetching.
views The views a visitor may switch between. A widget driven through el.events renders no switcher unless this attribute asks for one — a host app owns its own view chrome; views="none" is the opt-out for a fetched feed.
sort="none" Keep the host application's ordering instead of widget date sorting.
empty-message Customize the empty state shown after host-side filters.
eventActions(context) Return per-event actions with dynamic label, icon, placement, and pressed state.
eventClassName(context) Add host-owned state classes such as read, unread, saved, or canceled.
eventBadges(context) Add host-owned badges such as folder, collection, CFP, or saved state.

The ote-event-action event includes action, previewEvent, originalEvent, index, feed, and source. The widget renders only; it does not store favorites, folders, read state, or filters — nor the view a visitor picks in the switcher, which it reports as ote-view-change (detail: { view, previousView }) and writes neither to storage nor to your page's URL.
